# 建模方案

## 1. 模型类型与时间口径

模型为动态到单、允许批处理、具有首菜先后和截止时间约束的并行厨师调度问题。

时间采用统一连续时间轴，单位为分钟。离线模型描述一段完整历史；在线策略在时刻 t 只能使用 t 之前已经发生的信息。完整历史只能用于评价或理想基准，不能泄漏给在线策略。

## 2. 实体和参数

| 符号 | 含义 |
| --- | --- |
| M、N | 厨师数量、物理桌位数量 |
| i | 一桌顾客的一次用餐会话，换客后产生新会话 |
| a_i | 会话首次下单时间 |
| W_i、d_i | 首菜最大等待时长、截止时间，d_i=a_i+W_i |
| J_i | 该会话产生的全部需求单位集合 |
| j | 一份菜的需求单位；两份同菜拆为两个单位 |
| r_j、k_j | 该份菜下单时间、菜品类型 |
| Q_k | 菜品 k 单批最大制作份数 |
| p_k(q) | 菜品 k 合做 q 份的制作耗时 |
| delta_j | 完成后必要装盘、传菜耗时 |
| H_k | 菜品完成后允许的最大滞留时间，可选 |

加菜只会向 J_i 添加带有新 r_j 的需求，不改变 a_i。相同菜但口味或制作要求不兼容的需求，视为不同类型。

p_k(q) 使用输入表，不强制线性，也不假定合做一定节省时间。例如一份5分钟、两份7分钟、三份9分钟仅为示例。

## 3. 决策变量

将需求划分为制作批次 b，每批定义：

- J_b：批内需求集合。
- k_b、q_b：菜品类型、份数，q_b=|J_b|。
- m_b：执行厨师，取值1至M。
- s_b、c_b：开工和完成时间。
- U_j：需求 j 实际送达餐桌的时间。

决策包括如何分批、由谁制作、何时开工及何时送达。它是概念级约束模型；实现时可转为约束规划、混合整数规划或启发式策略，暂不指定求解器。

## 4. 制作约束

### 4.1 唯一服务

对有限历史中的全部已接受需求，批次集合构成需求集合的一个划分：每份需求恰好属于一个批次，不遗漏、不重复。

在线时，未完成需求可以继续等待；对完整有限输入的评价要求最终全部服务完毕。

### 4.2 合批兼容与容量

对每个批次 b：

```text
k_j = k_b                    对所有 j ∈ J_b
1 ≤ q_b ≤ Q_(k_b)
```

### 4.3 下单后才能开工

```text
s_b ≥ max{r_j : j ∈ J_b}
c_b = s_b + p_(k_b)(q_b)
```

初版不允许向已经开工的批次补入后来下单的需求，不考虑提前预制。

### 4.4 厨师互斥与不可中断

每批仅占用一名厨师。同一厨师的任意两个批次 b、b' 必须满足：

```text
c_b ≤ s_b'  或  c_b' ≤ s_b
```

已开工批次不能中断、换人或重排。

## 5. 完成与送达

若 j ∈ J_b，则 C_j=c_b，并要求：

```text
U_j ≥ C_j + delta_j
```

启用质量限制时还要求：

```text
U_j - C_j ≤ H_(k_j)
```

当前不显式限制传菜人员产能。最简版令 delta_j=0、U_j=C_j，避免引入送达决策。扩展版允许短暂等待，但必须用滞留上限或目标限制，不能通过无限放置成品来满足首菜顺序。

## 6. 首菜约束

令 E_i 为符合首菜定义的需求集合，默认 E_i=J_i，且非空。

```text
F_i = min{U_j : j ∈ E_i}
F_i ≤ d_i
若 a_i < a_h，则 F_i ≤ F_h
```

同一时刻首次下单的桌默认不规定先后；如需确定顺序，可使用接单序号。公平规则作用于首菜实际送达，不限制其余菜的桌间顺序。

一个批次可同时服务多桌。某桌已经获得首菜后，其加菜只参与后续需求调度。

## 7. 后续等待与齐菜

单菜等待：

```text
L_j = U_j - r_j
```

最终齐菜时间及用时：

```text
T_i = max{U_j : j ∈ J_i}
Z_i = T_i - a_i
```

T_i 仅在历史完整后才能确定。在线策略可计算“已知需求预计齐菜时间”，但不能将其当成最终离桌时间。

为排除顾客尚未加菜的空档，定义桌 i 的待送达需求数：

```text
B_i(t) = |{j ∈ J_i : r_j ≤ t < U_j}|
```

断菜等待的操作定义：从首菜之后开始，只在 B_i(t)>0 时累计；每次上菜重置计时；B_i(t)=0 时停止并清零，之后新增加菜从加菜时重新计时。各计时间隔的最大值记为 G_i。首次上菜前的等待单独由 F_i-a_i 衡量。

这一定义避免将顾客吃完后过很久才加菜的空档算成后厨等待。G_i 先作为评价或软目标，后续可设置上限。

## 8. 无解与降级模型

严格版本要求全部首菜时限成立；若无解，必须报告，不得将违规结果标为可行。

另设允许超时的降级版本：

```text
xi_i ≥ 0
F_i ≤ d_i + xi_i
```

首菜顺序仍保持硬约束。xi_i 用于量化承诺缺口。降级求解不等于首菜服务达标，结果必须标注超时桌数和程度。

## 9. 目标体系

推荐采用分层优化；每层在不损害前一层最优结果的前提下优化：

1. 严格模型优先寻找可行解；降级模型先最小化最大首菜超时，再最小化超时总和。
2. 控制最糟等待，例如最小化最大单菜等待，或最大断菜等待；二者的优先顺序需在实验前固定。
3. 降低整桌齐菜用时总和 sum_i Z_i。
4. 在上述结果相同时，降低总制作工时 sum_b p_(k_b)(q_b)。

这是一种待验证的默认偏好，并非业务定律。可通过实验比较其他层级，但不能在比较结果后随意更改成功标准。长等待限制设得越严格，合做和优先完成小单的自由度越小。

## 10. 在线运行

状态包括已发生订单、各桌已上菜情况、未开工需求、厨师当前批次和剩余耗时。新订单、加菜、批次完成和菜品送达均可触发更新；若策略允许主动等候合批，还需支持定时唤醒，避免无人触发而永久等待。

每次更新：

1. 冻结已执行结果和正在制作批次。
2. 更新未开工需求及首菜剩余时限。
3. 对已知需求重新分批、排序和分配。
4. 向空闲厨师提交当前要开工的批次，或决定有限时长等待。
5. 后续计划只作预测，可被新事件替换。

不能预知未来加菜，基础在线模型也不要求预测其概率。未来可另行加入统计预测，但需与无预测策略分别比较。

## 11. 桌位与翻台扩展

当前会话的在店区间和桌位分配作为输入，任意时刻在店会话数不超过N。若只回放已下单记录，N不会独立创造厨房约束。

扩展接待模型时，加入到店时间、人数、桌型、离桌时间 D_i、清台耗时和等位/放弃行为。同一物理桌的后续会话必须在前桌离开并清台后才能入座。D_i 应由用餐过程决定，不能直接等同于 T_i。

## 12. 渐进版本

| 版本 | 启用范围 |
| --- | --- |
| V0 | 动态首次点单、多厨师、单份制作、首菜顺序与时限、完成即送达 |
| V1 | 加入老桌加菜 |
| V2 | 加入同菜合批、容量与批量耗时 |
| V3 | 加入后续等待目标、传菜耗时及成品滞留限制 |
| V4 | 加入用餐、离桌、等位和接待量模型 |

每个版本均保留无解报告与相同输入比较原则。首菜时限也可先作为软目标探索，但必须明确其不是满足原始硬约束的版本。
