# 评价指标与实验方案

## 1. 要验证的命题

在厨师数量、需求事件、工时和首菜公平要求相同的条件下，新策略是否减少首菜超时和等待，同时避免把代价集中转移给大单或加菜顾客。

不以某一个综合分数替代原始指标。评价至少覆盖服务底线、整体等待、长等待和资源消耗。

## 2. 核心指标

| 指标 | 定义 | 解释 |
| --- | --- | --- |
| 首菜顺序违规次数 | 首菜时间序列中违反首次下单先后关系的桌对数量 | 硬约束，要求为0；同刻下单不比较 |
| 首菜超时率 | 首菜超过截止时间的会话数/会话总数 | 服务承诺兑现程度 |
| 首菜超时量 | max(0,F_i-d_i) 的均值、最大值 | 均值按全部会话计算；另列仅超时会话均值 |
| 首菜等待 | F_i-a_i 的均值、P90、最大值 | 开始吃饭前的等待 |
| 单菜等待 | U_j-r_j 的均值、P90、最大值 | 以每份菜为单位，另列加菜需求 |
| 最长断菜等待 | G_i 的P90、最大值 | 使用建模文档中“有未送达需求时才计时”的定义 |
| 整桌齐菜用时 | T_i-a_i 的均值、P90 | 相同加菜轨迹下比较，不等同于占桌时间 |
| 总制作工时 | sum_b p_(k_b)(q_b) | 检验合做是否节省工作量 |
| 成品滞留时间 | U_j-C_j 的均值、最大值 | 检查是否靠放置成品兑现顺序 |

P90采用固定分位数计算方法，实验代码和报告中注明。小样本应展示原始分布，避免过度解释分位数。

顺序违规使用“桌对数量”而非模糊的“违规次数”；如另统计受影响桌数，必须使用不同名称。

## 3. 公平性分组

分别按小、中、大工作量订单统计首菜、单菜和齐菜等待，并单列加菜。工作量使用各份单独制作耗时之和，不只看菜数。

离线评价可按最终全部需求分组；在线策略只能使用当时已知工作量。分组边界在实验前固定，同一组实验使用相同边界。

首菜顺序公平不能替代后续服务公平。重点检查平均等待改善是否伴随大单P90或最大等待显著恶化。

## 4. 辅助指标

- 单位时间出菜份数、完成会话数及观察截止时剩余需求量。
- 有可开工需求时的厨师空闲时间；主动等候合批也计入，但不直接判为错误。
- 合做批次数、平均批量和节省工时，用来解释机制，不直接作为成功标准。

不以忙碌率越高越好：合做可能让厨师更早完成工作、空闲增加，同时顾客等待下降。

## 5. 翻台与接待量指标

启用完整用餐与等位模型后，再评价：

- 每小时完成用餐的桌数和人数。
- 入座到离桌的占桌时间。
- 到店到入座的等位时间。
- 放弃等位比例。

到店需求量与实际完成接待量必须分开。固定需求回放下，需求数量相同，不能宣称系统增加了到店客流。只有存在未满足需求时，更早释放桌位才可能带来更多接待。

## 6. 比较基准

至少比较以下策略，并明确每种策略的具体规则：

1. 整桌先到先做：用于展示最初提出的阻塞现象，不假定这就是门店实际做法。
2. 简单穿插策略：保障首菜顺序，优先处理紧迫首菜；后续按菜品下单时间处理，合做采用固定规则。
3. 新调度策略：综合时限、剩余工作和合做收益。

如果实现离线全知求解器，可作为理想参照：它能看到未来全部需求，不能当作可部署在线策略；限时求解得到的可行解也不能直接宣称是全局最优或严格下界。

各策略使用相同的厨师、批量容量、工时和送达规则。基准也必须明确首菜顺序如何执行；约束不一致的结果应单独报告，不能当成同条件改善。

## 7. 输入与实验场景

复用同一条事件轨迹：首次点单、加菜、菜品类型、份数、时间和会话归属一致。在线策略逐事件接收，不提前读取未来记录。

覆盖下列情形：

- 低负载、接近饱和、持续超载。
- 大小单交错、前桌慢菜、短时间集中下单。
- 同菜比例高/低、合做收益高/低。
- 加菜少/多、加菜早/晚。
- 首菜时限宽松/紧张、严格约束本身无解。

固定加菜时间是受控实验假设。现实加菜可能受上菜进度影响，后续需增加顾客行为模型，不能将固定轨迹结果直接视为真实经营收益。

## 8. 统计口径

1. 选定到单观察窗口，停止产生新需求后继续仿真，直到窗口内全部需求完成。
2. 单独报告观察截止时的完成量和积压量，不能只计算已完成订单的等待。
3. 若长时间没有进展或无法完成，报告失败及未服务需求，不删除样本。
4. 随机生成数据时，多个策略使用相同随机种子与轨迹，运行多组轨迹。
5. 对每组轨迹计算成对差值，再报告平均改善及波动；样本足够时给出置信区间。
6. 同时给出绝对差（分钟、百分点）和相对变化；基准为0时不计算相对改善率。

## 9. 第一阶段的通过标准

暂不人为承诺“至少提升百分之多少”。先验证：

- 资源、唯一服务、合批兼容和不可中断约束均成立。
- 首菜顺序违规为0。
- 可行场景中是否满足首菜期限；无解场景是否被正确区分。
- 相对简单穿插基准，首菜超时、单菜等待或齐菜时间至少一项有稳定改善。
- 其他关键等待指标及大单、加菜分组没有不可接受的恶化。

“不可接受”的阈值需在正式实验前确定；若部分指标改善、部分恶化，应报告权衡，不笼统宣称更好。

## 10. 最小验证样例

先手工构造以下小例子检查定义，再进行批量仿真：

1. 一位厨师，前桌六道菜、后桌一道菜：验证首菜顺序下的穿插。
2. 两位厨师，前桌慢首菜、后桌快首菜：验证并行不等于可以违反送达顺序。
3. 老桌出齐后较晚加菜：验证不重置首菜、不错误累计顾客自行等待空档。
4. 两桌同菜合做：验证容量、工时、分配和送达规则。
5. 为凑合批将导致首菜超时：验证服务约束优先。
6. 前桌唯一慢菜导致后桌时限不可满足：验证无解与降级结果。
