# 第一版实现与运行说明

## 1. 运行环境

Python 3.9及以上，仅使用标准库，无需安装第三方依赖。HTTP 服务用于本地原型验证，默认只监听本机；不具备生产服务所需的认证、持久化与部署保障。

```bash
cd /Users/a1/work/code/littlelife/easy_office/easy_cooker
python3 main.py --chefs 2 --tables 8 --first-course-seconds 900
```

服务地址为 `http://127.0.0.1:8000`，按 Ctrl+C 停止。所有状态保存在内存中，重启清空；只运行一个服务进程。

### 验证已经启动的 HTTP 服务

保持 `main.py` 运行，在另一个终端执行：

```bash
cd /Users/a1/work/code/littlelife/easy_office/easy_cooker
python3 verify_http.py --table 1
```

脚本实际请求运行中的服务，依次验证健康检查、菜单、首次下单、同一请求重试、加菜和任务状态。它会真实新增两份菜，请选择空闲桌；再次运行可以指定其他空闲桌号，例如 `--table 2`。自定义服务地址使用 `--base-url http://127.0.0.1:8001`。

脚本会输出当前任务的完成命令。达到制作时长后执行该命令，验证完成反馈及后续任务分配。默认最快菜需要180秒，提前完成返回409是预期行为。完成两份菜后，使用脚本输出的关闭会话命令释放桌位。

### 不启动服务的核心逻辑演示

`demo.py` 直接调用核心服务对象，不请求 `main.py`。无需启动服务器即可运行完整逻辑演示：

```bash
python3 demo.py
```

演示使用可推进的模拟时钟，包括两桌点单、老桌加菜、穿插制作和完成任务，无需真实等待。

运行测试：

```bash
python3 -m unittest discover -s tests -v
```

HTTP 集成测试会临时监听本机随机端口。

## 2. 分层结构

| 模块 | 职责 |
| --- | --- |
| `app/api.py` | HTTP请求接收、JSON响应和错误码 |
| `app/schemas.py` | 输入校验和请求格式 |
| `app/service.py` | 下单、加菜、完成、关闭会话与调度触发 |
| `app/domain.py` | 固定菜单和领域记录 |
| `app/scheduler.py` | 选择下一份待制作菜，后续可替换策略 |
| `app/store.py` | 内存存储及统一互斥锁 |
| `app/clock.py` | 真实时钟和可控模拟时钟 |
| `main.py` | 服务启动和参数 |
| `demo.py` | 无服务器的完整示例 |

所有状态访问通过服务层，状态变更与任务分配在同一把锁内串行完成。厨师读取任务不会触发重新规划。调度器选择需求，服务层创建任务并更新厨师占用。

## 3. 实际调度规则

1. 未上首菜的桌按首次接单顺序排列，同时间也使用接收序号确定先后。
2. 最早未上首菜的桌，如果尚无制作中需求，优先启动其最早登记的一份需求。
3. 该桌首菜完成之前，不启动后桌首菜，也不为该桌启动第二份菜。
4. 已上首菜的桌，其剩余需求按登记顺序穿插分配给其他空闲厨师。
5. 下单、加菜、完成任务时统一调度；已经开工的任务保持不变。

本版分配即开工，完成即上桌，每份菜一个任务，不合做。没有尚未开工的“厨师专属队列”；全局待做需求保留在核心层，厨师获取的是当前任务。这样不用反复撤回尚未执行的厨师任务。

同一请求的菜品条目会合并数量并按菜品编号规范化，原始条目顺序不作为顾客要求的上菜顺序。当前不自动选择最短菜作为首菜。

保守首菜规则会损失并行能力，但保证首菜顺序。它是后续优化策略的基准，不代表完整模型的最优解。首菜截止时间用于状态监测，尚未用于截止时间优化、提前风险预测或严格可行性证明。

## 4. 时间、重试和会话

- 时间统一使用 Unix 时间戳，耗时单位为秒，界面未来可转成本地时间。
- HTTP下单时间由服务端接收时记录，客户端不能传 `ordered_at`。回放实验通过注入模拟时钟决定事件时间。
- `request_id` 是全局唯一幂等键：同一内容重试返回原始结果，不重复下单；不同内容使用同一个键返回409。
- 首次点单不传 `session_id`，创建本次用餐会话；加菜必须携带返回的同一个会话编号及桌号。
- 一桌只允许一个未关闭会话。全部菜上完后仍可加菜；只有显式关闭才释放桌位。
- 完成反馈携带明确任务编号，重复反馈不会误完成下一项任务。
- 完成时间不能早于预定制作耗时。时间到了不会自动完成，必须由厨师反馈；延迟反馈会形成实际等待。

## 5. 接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/health` | 健康检查 |
| GET | `/menu` | 固定菜单及制作耗时 |
| POST | `/orders` | 首次下单或加菜 |
| GET | `/chefs/1/task` | 查看厨师1当前任务，无任务时返回null |
| POST | `/chefs/1/tasks/{task_id}/complete` | 完成当前任务，触发后续调度 |
| GET | `/sessions/{session_id}` | 查看整桌需求及首菜状态 |
| POST | `/sessions/{session_id}/close` | 全部菜上完后关闭会话 |
| GET | `/state` | 查看全局状态，便于调试 |

成功返回200；参数错误400；不存在404；状态或幂等冲突409；无有效长度或过大的下单请求体413。首菜状态包含 `waiting`、`overdue`、`on_time`、`late`。

### 查询菜单

```bash
curl http://127.0.0.1:8000/menu
```

### 首次下单

```bash
curl -X POST http://127.0.0.1:8000/orders \
  -H 'Content-Type: application/json' \
  -d '{"request_id":"order-a-001","table_id":1,"items":[{"dish_id":"greens","quantity":2},{"dish_id":"fried_rice","quantity":1}]}'
```

响应包含 `accepted`、`order_id`、`session_id`、`ordered_at` 和 `first_course_deadline`。下单成功仅表示需求接受，不保证首菜一定按时。

### 加菜

将以下 `SESSION_ID` 替换为首次下单返回的会话编号：

```bash
curl -X POST http://127.0.0.1:8000/orders \
  -H 'Content-Type: application/json' \
  -d '{"request_id":"order-a-002","table_id":1,"session_id":"SESSION_ID","items":[{"dish_id":"tomato_eggs","quantity":1}]}'
```

### 查询和完成厨师任务

```bash
curl http://127.0.0.1:8000/chefs/1/task
```

等待该任务规定制作时长后，将 `TASK_ID` 替换为返回的任务编号：

```bash
curl -X POST http://127.0.0.1:8000/chefs/1/tasks/TASK_ID/complete
```

固定菜单耗时为180至420秒。快速验证请使用 `demo.py` 的模拟时钟，不需要修改真实时钟或绕过完成时长检查。

## 6. 当前覆盖与后续扩展

已覆盖请求接收、校验、幂等、首次下单、加菜、首菜顺序、厨师互斥、任务不可中断、完成后的调度、桌位复用和首菜超时状态。
